# WP-1.2 — Auth + Rollen/Mandanten — Design-Spec

> Status: Entwurf v1 (2026-07-11) · Branch `feat/platform-foundation` · Phase 1
> Bezug: [Masterplan §10 WP-1.2](../../POWERHOUSE_360_MASTER_PLAN.md), [SECURITY_AND_PERMISSIONS.md](../../SECURITY_AND_PERMISSIONS.md), [DATA_MODEL.md §3](../../DATA_MODEL.md), [API_ARCHITECTURE.md](../../API_ARCHITECTURE.md), [ADR-002](../../DECISIONS/ADR-002-postgres-prisma-better-auth.md)
> Gates: **F-02** (Mandant & Rollen), **F-19** (Audit-Vollständigkeit), **F-20** (Berechtigungs-Negativmatrix)

## 1. Ziel & Abgrenzung

WP-1.2 ersetzt die interim HTTP-Basic-Auth (`apps/platform/src/middleware.ts`) durch echte Authentifizierung, ein serverseitig erzwungenes Rollen-/Rechtemodell und Mandantentrennung. Ergebnis: Man legt Organisationen an, lädt Nutzer mit Rolle ein, und jeder Zugriff wird serverseitig gegen Permission **und** Org-Scope geprüft (deny-by-default). Ein Audit-Log-UI macht sicherheitsrelevante Ereignisse sichtbar.

**Bestätigte Grundentscheidungen (2026-07-11):**
1. **better-auth = nur Authentifizierung** (User/Session/Account/Verification). Mandant + Rollen/Permissions/Scopes/Einladungen sind **eigene Domain-Tabellen/Code**. Das better-auth Organization-Plugin wird **nicht** verwendet.
2. **RBAC-Kern jetzt**, TOTP-2FA und Bewohner-Magic-Link **verschoben** auf spätere WP.

## 3. Paketstruktur (neu)

```

  src/permissions.ts    # typisierter Katalog (const + Union-Typ Permission)
  src/roles.ts          # SystemRole-Enum + ROLE_PERMISSIONS: Record<SystemRole, Permission[]>
  src/can.ts            # resolvePermissions(roles), roleHasPermission(role, perm) — pure
  src/index.ts
packages/auth          # better-auth-Instanz + serverseitige Guards
  src/auth.ts           # betterAuth({...}) mit prismaAdapter, emailAndPassword, emailVerification
  src/context.ts        # getAuthContext(headers) -> { user, memberships[] }
  src/guard.ts          # requirePermission(ctx, perm, {organizationId}); assertOrgScope; AuthzError/AuthnError
  src/email.ts          # schreibt DomainEvents für Auth-Mails (statt direktem SMTP)
  src/client.ts         # better-auth/react createAuthClient (für Login/Invite-Form)
  src/index.ts
packages/testing        # Test-DB-Helper + Factories
```

## 4. Datenmodell — eine Migration `auth_and_rbac`

### 4.1 better-auth-Tabellen (von better-auth verwaltet, `@@map` snake_case)
- `user`: `id String @id` (better-auth-String-ID), `name`, `email @unique`, `emailVerified Boolean`, `image String?`, `createdAt`, `updatedAt`, **additionalField** `locale String @default("de")`. (`lastLoginAt` optional via databaseHook — kann später kommen.)
- `session`: `id`, `expiresAt`, `token @unique`, `ipAddress?`, `userAgent?`, `userId → user`, timestamps.
- `account`: better-auth-Standard (hält u. a. Passwort-Hash), `userId → user`.
- `verification`: `identifier`, `value`, `expiresAt`.

Schema wird per `better-auth` CLI generiert und dann in `schema.prisma` eingepflegt (Stil an Bestand angleichen: `@@map`, snake_case). IDs der better-auth-Tabellen bleiben String (kein `@db.Uuid`).

### 4.2 Eigene Domain-Modelle
```prisma
enum SystemRole {
  PLATFORM_ADMIN
  SALES
  OPERATIONS
  SERVICE
  FINANCE
  PROPERTY_MANAGER
  OWNER_BOARD
  BILLING_CONTACT
  INSTALLER_PARTNER_ADMIN
  INSTALLER
  RESIDENT
  PARKING_USER
}

enum MembershipStatus { ACTIVE  SUSPENDED }
enum InvitationStatus { PENDING  ACCEPTED  REVOKED  EXPIRED }

model OrganizationMembership {
  id             String @id @default(uuid()) @db.Uuid
  userId         String                     // -> user.id (better-auth String-ID)
  user           User   @relation(fields: [userId], references: [id], onDelete: Cascade)
  organizationId String @db.Uuid
  organization   Organization @relation(fields: [organizationId], references: [id])
  role           SystemRole
  status         MembershipStatus @default(ACTIVE)
  invitedById    String?
  createdAt      DateTime @default(now())
  updatedAt      DateTime @updatedAt
  @@unique([userId, organizationId])
  @@index([organizationId])
  @@map("organization_membership")
}

model Invitation {
  id             String @id @default(uuid()) @db.Uuid
  email          String
  organizationId String @db.Uuid
  organization   Organization @relation(fields: [organizationId], references: [id])
  role           SystemRole
  token          String @unique
  status         InvitationStatus @default(PENDING)
  invitedById    String?
  expiresAt      DateTime
  acceptedAt     DateTime?
  createdAt      DateTime @default(now())
  @@index([email])
  @@index([organizationId, status])
  @@map("invitation")
}
```
`Organization` bekommt Rück-Relationen `memberships` + `invitations`. Bestehende Lead/Audit-FKs bleiben unberührt.

> Hinweis: `Membership.role` ist zunächst **eine** Rolle je Org (unique[userId, organizationId]). Mehrfachrollen je Org sind YAGNI; falls später nötig → eigene `MembershipRole`-Zeilen.

## 5. Permission-Katalog & Rollen (WP-1.2, konkret)

**Permissions (Start-Set):** `lead.read`, `lead.update`, `audit.read`, `member.read`, `member.invite`, `member.assign_role`, `member.remove`, `organization.read`.

**Rollen → Permissions:**
| Rolle | Permissions (WP-1.2) |
|---|---|
| `PLATFORM_ADMIN` | alle |
| `SALES` | lead.read, lead.update, member.read, organization.read |
| `OPERATIONS` | lead.read, member.read, organization.read |
| `SERVICE` | lead.read, member.read, organization.read |
| `FINANCE` | lead.read, member.read, organization.read |
| `PROPERTY_MANAGER` | lead.read, organization.read |
| `OWNER_BOARD` | organization.read |
| `BILLING_CONTACT`, `INSTALLER_PARTNER_ADMIN`, `INSTALLER`, `RESIDENT`, `PARKING_USER` | (leer bis Feature existiert) |

Mitglieder-Verwaltung (`member.invite`, `member.assign_role`, `member.remove`) und `audit.read` sind in WP-1.2 **nur `PLATFORM_ADMIN`**. Das liefert für jede andere Rolle klare F-20-Negativfälle (z. B. `SALES` darf nicht `member.invite`, nicht `member.assign_role`, nicht `audit.read`).

## 6. Auth-Fluss

- **Login:** better-auth E-Mail+Passwort, DB-Sessions (Postgres), httpOnly-Cookie (`SameSite=Lax`). Route-Handler `apps/platform/src/app/api/auth/[...all]/route.ts` via `toNextJsHandler(auth)`. `nextCookies()` als letztes Plugin (Cookies aus Server-Actions).
- **E-Mail über Outbox (WP-1.1-Prinzip):** `emailVerification.sendVerificationEmail` und `emailAndPassword.sendResetPassword` schreiben je einen `DomainEvent` (`auth.verification_requested`, `auth.password_reset_requested`); der Invite-Flow schreibt `member.invited`. `apps/worker` bekommt Handler dafür → Versand über bestehenden Mailer.
- **Einladung:** `POST`-Server-Action (Guard `member.invite`) → `Invitation` (Token, `expiresAt = now+7d`) + Outbox `member.invited` + `AuditEvent(action="member.invited")`. Worker mailt Link `/invite/{token}`.
- **Accept:** `/invite/[token]` prüft Token/Status/Ablauf → Formular (Name + Passwort) → Server-Action: `auth.api.signUpEmail` → `OrganizationMembership(role aus Invite)` + `invitation.status=ACCEPTED, acceptedAt` + `user.emailVerified=true` (Invite beweist E-Mail-Besitz) + `AuditEvent(action="member.joined")`. Alles in einer Transaktion, wo möglich.
- **Erst-Admin (ersetzt `ADMIN_BASIC_*`):** idempotentes Script `packages/auth` → `pnpm ph360:create-admin` liest `ADMIN_EMAIL`/`ADMIN_PASSWORD`, legt (falls fehlend) verifizierten `PLATFORM_ADMIN`-User + Membership in der Powerhouse-Org an.

## 7. Enforcement (serverseitig, deny-by-default)

- `getAuthContext(headers)` → Session via `auth.api.getSession` → lädt `user` + aktive `memberships` (org + role).
- `requirePermission(ctx, permission, { organizationId })`:
  1. keine Session → `AuthnError` (→ Redirect `/login` bzw. 401 an API).
  2. keine aktive Membership in `organizationId` → `AuthzError` (403) + `AuditEvent(action="authz.denied")`.
  3. `resolvePermissions(membership.role)` enthält `permission` nicht → `AuthzError` (403) + Audit.
- `assertOrgScope(ctx, organizationId)` → Kurzform für „Membership in dieser Org vorhanden".
- **Tenant-scoped Reads** (Leads, Audit): immer `where: { organizationId }` aus dem geprüften Scope. Vollautomatischer Prisma-Wrapper (SECURITY §1.2) = spätere Härtung.
- **Middleware** (`apps/platform`): optimistischer Cookie-Check via `getSessionCookie(req)` auf `/admin/:path*` → fehlt → Redirect `/login`. Echte Permission-Prüfung im jeweiligen Server-Component/Server-Action (nicht in der Middleware).

## 8. UI (apps/platform)

| Route | Inhalt | Guard |
|---|---|---|
| `/login` | E-Mail+Passwort-Formular (better-auth client) | — (öffentlich) |
| `/invite/[token]` | Invite-Ansicht + Name/Passwort → Accept | gültiger Token |
| `/admin` (Layout) | Auth-Shell: lädt Kontext, Nav (Leads · Mitglieder · Audit), zeigt User + Logout | Session + Membership |
| `/admin/leads` | Bestehende Liste, jetzt geschützt | `lead.read` |
| `/admin/members` | Mitgliederliste + Invite-Form + offene Invites + Rollenwechsel | `member.read` / `member.invite` / `member.assign_role` |
| `/admin/audit` | AuditEvent-Liste mit Filtern (Aktion, SubjectType, Zeitraum, Akteur) | `audit.read` |

Leere-/Fehler-/Ladezustände je Seite (DoD). UI-Ausblendung ist Ergonomie, nie Sicherheit — jede Aktion serverseitig geprüft.

## 9. Audit (F-19)

Neu auditierte Aktionen: `auth.login` (databaseHook on session create), `member.invited`, `member.joined`, `member.role_changed`, `member.removed`, `authz.denied`. Bestehendes `AuditEvent`-Modell wird wiederverwendet (`actorType=USER`, `actorId=user.id`, `organizationId`, `requestId`). Anzeige über `/admin/audit`.

## 10. Tests & Definition of Done

- **Unit (Vitest, `packages/permissions`):** `resolvePermissions`/`roleHasPermission`; vollständige **Negativmatrix** (jede Rolle × verbotene Permissions → false) — Kern von **F-20**.
- **Integration (Vitest + `packages/testing`, echtes Postgres):**
  - **F-02:** Org A + Org B, User mit `SALES`-Membership in A. `lead.read` auf A-Lead → ok; auf B-Lead → 403; `AuditEvent(authz.denied)` geschrieben.
  - **F-19:** Invite→Accept erzeugt `member.invited` + `member.joined`; Rollenwechsel erzeugt `member.role_changed`; Login-Hook erzeugt `auth.login`.
  - **F-20:** je getesteter Rolle ≥3 verbotene Aktionen über `requirePermission` → 403 (Guard-Ebene + mind. eine Route-Ebene).
  - Invite-Lebenszyklus: PENDING→ACCEPTED, abgelaufener/again-accept Token → Fehler.
- **Browser-Verifikation (Preview-Tools, dokumentiert im IMPLEMENTATION_LOG):** unauth `/admin` → Redirect `/login`; Login → `/admin/leads` sichtbar; Invite anlegen → Mail in Mailpit → Accept → Mitglied erscheint.
- **DoD zusätzlich:** `pnpm typecheck` + `pnpm lint` grün; Migration läuft gegen leere DB; keine Mock-Daten im Produktivpfad; Marketing-Site unberührt (F-21 nicht regredieren).

CI (GitHub Actions) bleibt an R-02 (kein Remote) gekoppelt — Tests laufen zunächst lokal; Pipeline-Datei wird vorbereitet, sobald Remote existiert.
